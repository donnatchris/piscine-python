3. CORRECTIONS PRIORITAIRES

3.1 P1 - Valider chaque élément de la liste dans apply_limit

Référence : PDF page 5, liste d'entiers ou de flottants et traitement des
arguments incorrects.
Fichier : ex00/give_bmi.py:162-166.

La fonction vérifie que bmi est une liste et limit un entier. Elle ne vérifie
pas que chaque élément de bmi est un int ou un float, alors qu'une fonction
assert_is_number_list existe déjà aux lignes 68-80.

Résultats observés :

    apply_limit([[20, 30]], 26)  -> [[False, True]]
    apply_limit([True, False], 0) -> [True, False]
    apply_limit(["20"], 26)     -> exception NumPy lors de la comparaison

Le premier cas accepte une liste imbriquée et renvoie une liste de listes
au lieu du contrat list[bool]. Le deuxième accepte des booléens alors que
give_bmi les rejette et que le sujet demande des int ou float.

Correction : utiliser une validation élément par élément, cohérente avec
give_bmi, avant la conversion NumPy. Cette validation peut lever une
exception explicite que le programme appelant intercepte ; un try/except
interne et une valeur de secours ne sont pas imposés par cette correction.

À conserver : la comparaison stricte « > » est correcte.
apply_limit([25, 26, 27], 26) renvoie bien [False, False, True].
Il ne faut pas remplacer cette comparaison par « >= ».

3.2 P1 - Conserver les trois dimensions dans ft_grey

Référence : PDF page 12, les cinq filtres doivent conserver la même forme
d'image.
Fichier : ex05/pimp_image.py:104-119, particulièrement la ligne 118.

np.sum(array, axis=2) supprime la dimension des canaux. La conversion de type
qui suit ne rétablit pas cette dimension.

Exemple reproductible :

    import numpy as np
    from pimp_image import ft_grey
    image = np.array([[[10, 20, 30], [255, 0, 0]]], dtype=np.uint8)
    image.shape           # (1, 2, 3)
    ft_grey(image).shape  # (1, 2) actuellement

Avec l'image locale, on passe de (491, 740, 3) à (491, 740).
L'affichage paraît bien gris, mais cela ne suffit pas à respecter le contrat.

Correction : calculer l'intensité grise et la reporter dans les trois canaux
R, G et B. Le résultat doit avoir exactement array.shape et des composantes
égales pour chaque pixel. Mettre à jour la docstring qui annonce actuellement
un retour 2D.

Le sujet n'impose pas de formule précise de luminance : la moyenne actuelle
n'est pas, en elle-même, le défaut constaté. Respecter les restrictions
d'opérateurs lors de la correction, notamment l'absence de « + » explicite
dans ft_grey.

3.3 P1 - Afficher les images transformées via les fichiers à rendre

Référence : PDF pages 13 et 14. Le test appelle directement les cinq fonctions,
et la page suivante impose l'affichage des images transformées.

Les fonctions renvoient leurs tableaux mais ne créent aucune figure et

Ton tester.py affiche certaines valeurs renvoyées dans un second temps,
mais ce fichier ne fait pas partie des fichiers à rendre. Le test du sujet,
qui appelle simplement ft_invert(array), ft_red(array), etc., n'obtiendra
donc aucun affichage avec le module actuel.

Correction : faire assurer l'affichage par les fonctions publiques ou par
un auxiliaire qu'elles appellent dans pimp_image.py, tout en renvoyant le
tableau transformé. Prévoir l'affichage des cinq filtres, dont le vert.
L'original peut servir de vue de référence comme sur la figure du sujet.

Défaut supplémentaire du test local : ex05/tester.py:31-35 affiche Original,
Invert, Red, Blue et Grey, mais aucun Green. L'appel de la ligne 25 calcule
le vert puis abandonne le résultat. Ajouter sa présentation si le tester
est conservé ; éviter de multiplier les fenêtres une fois que les fonctions

4. AUTRES CORRECTIONS ET ÉCARTS

4.1 P2 - Éviter de modifier les valeurs dans slice_me

Référence : PDF page 6, renvoyer une version tronquée du tableau reçu en
utilisant le slicing.
Fichier : ex01/array2D.py:44-53.

La conversion np.array(family) impose un type commun à toutes les cellules.
Elle peut ainsi modifier les valeurs avant même de les découper.

Cas observés :

    slice_me([[1, "a"], [2, "b"]], 0, 1)
    # Renvoie [["1", "a"]] au lieu de [[1, "a"]].

    slice_me([[9007199254740993, 0.0]], 0, 1)
    # Renvoie [[9007199254740992.0, 0.0]].

Le deuxième cas est aussi un tableau purement numérique : il montre une
perte réelle de précision, au-delà d'un simple changement de type.

Correction : conserver les données originales pour le résultat du slicing,
ou utiliser une représentation qui ne les convertit pas implicitement.
Le slicing Python d'une liste satisfait aussi l'exigence de découpage ;
NumPy n'est pas obligatoire. Continuer à afficher les deux bonnes formes.

5. POINTS AMBIGUS ET AMÉLIORATIONS NON EXIGÉES EXPLICITEMENT

5.1 Signification de « format » dans l'exercice 02

La page 7 dit d'afficher le « format » et le contenu RGB de l'image, mais
l'exemple n'affiche que la forme du tableau et ses pixels. Ton chargeur
affiche cette forme et renvoie le tableau, dont print(ft_load(...)) affiche
les pixels exactement selon ce protocole.

Si « format » signifie le format de fichier, il manque par exemple JPEG et
le mode RGB dans la sortie. Ce point reste une ambiguïté du texte face à
l'exemple ; il n'est pas établi comme un échec des tests fournis.
Ne pas ajouter automatiquement un second print des pixels dans ex02 :
le print du test les affiche déjà, ce qui créerait un doublon.

5.2 Données des images différentes de celles de l'exemple

Les fichiers locaux montrent un papillon. Ils ne correspondent ni au raton
laveur ni au paysage des figures du sujet.

Dimensions observées :

- ex02/landscape.jpeg : 244 x 148 pixels, RGB, format JPEG ;
- ex03/animal.jpeg et ex04/animal.jpeg : 740 x 491 pixels, RGB ;
- ex05/landscape.jpg : 740 x 491 pixels, RGB, format JPEG.

Cela explique les différences de tailles et de pixels dans les sorties.
Il ne faut pas coder en dur les dimensions ou les valeurs des exemples pour
les faire disparaître. Si les ressources originales sont fournies avec
la mission, utiliser ces ressources pour reproduire les illustrations.
L'énoncé autorise explicitement des zones et tableaux de zoom différents.
Je ne classe pas le choix du papillon comme un défaut algorithmique.

Les commentaires « Expected output » de tes tests d'images reprennent les
dimensions du PDF plutôt que celles de tes fichiers. Les adapter aux données
locales, ou préciser qu'ils illustrent la sortie avec l'image du sujet.

5.3 Valeurs numériques particulières dans give_bmi

Le contrôle de positivité rejette les poids nuls ou négatifs, alors que le
texte ne détaille pas ces cas. Une taille strictement positive est nécessaire
pour le calcul usuel, mais la politique sur le poids n'est pas explicitée.
Ce choix doit être cohérent et documenté ; il n'est pas présenté ici comme
une obligation d'accepter des valeurs physiquement impossibles.

Une taille infinie est acceptée et produit 0.0 ; une taille positive de
1e-200 produit inf et un RuntimeWarning à cause du calcul flottant.
Rejeter les valeurs non finies et traiter les débordements renforcerait
la robustesse. L'énoncé ne définit pas précisément ces cas extrêmes :
ils ne sont pas confondus avec le défaut de validation confirmé en 3.1.

5.4 Main dans les modules de fonctions

La règle générale demande un main pour chaque programme, mais ex00, ex01,
ex02 et ex05 demandent des modules de fonctions testés par import.
Ne pas déclarer automatiquement ces modules invalides parce qu'ils n'ont
pas de main de démonstration. Toute démonstration ajoutée doit cependant
être protégée et ne produire aucun effet lors de l'import.

5.5 P3 - Lieu d'interception des exceptions dans les modules de fonctions

Référence : PDF page 4 : « Any exception not caught will invalidate the
exercices, even in the event of an error that you were asked to test. »

Cette règle est générale : le sujet ne la réserve pas aux programmes ayant
un main. En revanche, il ne précise pas que chaque fonction doit intercepter
elle-même ses exceptions. Une fonction peut détecter un argument invalide,
lever une exception et laisser le programme appelant l'intercepter, par
exemple dans son main. La détection et l'interception sont deux responsabilités
distinctes.

Observations sur les fonctions testées :
- ex00/give_bmi.py:134-136 : des listes de longueurs différentes provoquent
  une AssertionError avec le message « the arguments are bad » ;
- ex01/array2D.py:30-46 : une liste irrégulière ou non 2D provoque une
  AssertionError avec le même message ;
- ex05/pimp_image.py:24-28 : une entrée ne représentant pas une image RGB
  provoque une AssertionError ;
- ex03/load_image.py, ex04/load_image.py et ex05/load_image.py : les erreurs
  de lecture sont propagées, notamment FileNotFoundError pour un chemin absent.

Ces exceptions sont observables lors d'appels directs sans interception.
Leur propagation hors d'une fonction ne démontre pas, à elle seule, une
violation de la règle : le programme appelant peut les intercepter.
Sans précision supplémentaire sur le protocole d'évaluation des fonctions,
l'absence de try/except interne reste un point d'interprétation, et non
une non-conformité confirmée des exercices 00, 01 ou 05.

Pour les programmes complets, éviter qu'une exception sorte du point
d'entrée sans traitement. Les main de zoom.py et rotate.py interceptent
déjà les exceptions : les lancements avec une image absente affichent
un message clair sans traceback.

Pour les modules de fonctions, conserver une politique d'erreur cohérente
et documentée, puis prévoir l'interception dans le programme de test appelant
si les fonctions lèvent des exceptions. Il n'est pas nécessaire de remplacer
systématiquement les exceptions par None ou un tableau vide.
Le défaut de validation de apply_limit décrit en 3.1 reste distinct :
accepter une liste imbriquée et renvoyer une liste de listes ne respecte
pas le contrat attendu, quel que soit le lieu choisi pour l'interception.
